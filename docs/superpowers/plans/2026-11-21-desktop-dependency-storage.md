# 桌面工程依赖的同盘与跨盘复用计划

目标是让 Windows x64 完整版在断网时，把依赖文件按卷复用。Studio 装在 C 盘，用户在 D 盘的两个不同目录建工程时，首个工程承担 D 盘缓存的准备成本，第二个工程只增加自己的依赖目录结构和少量工程文件。

沿用 Electron、Node 和随包 pnpm 10.33.0。各工程保留自己的 `package.json`、锁文件、`vendor/` 和 `node_modules`。两个工程可以选用不同的依赖版本。工作从 [桌面安装入口](../../../desktop/runtime.cjs)、[工程准备判断](../../../desktop/projects.cjs) 和 [离线资源准备](../../../desktop/scripts/prepare-offline.cjs) 开始。

## 选定的方案

| 使用情形 | 安装行为 |
| --- | --- |
| 轻量版 | 继续由 pnpm 根据工程位置和配置选择 store，优先使用缓存。验证跨卷创建的第二个工程确实复用首次下载的文件。 |
| 完整版，工程与随包 store 同卷 | 直接从随包 store 以 pnpm 的 `auto` 方式导入。匹配基线的工程继续冻结锁文件、离线安装并跳过安装脚本。 |
| 完整版，工程在另一卷 | 从工程目录用内置的 pnpm 查询 `store path`。目标 store 与工程同卷、可写且在工程外时，从随包基线补齐缓存，再以该 store 安装。之后，同卷不同目录的工程复用它。 |
| 目标卷无法共享 | 目标 store 不可写、位于工程内、指向另一卷，或已确认文件系统只能复制时，完整版直接从随包 store 安装，日志说明原因。沿用本机和工程已有的 pnpm 配置文件，选址仅作用于本次桌面安装。 |

上次在 Linux/ext4 按 Windows x64 目标安装，标准依赖的共享 store 约 508 MiB。同一离线锁文件下，每个工程强制复制新增 544.3 MiB，使用硬链接新增 25.4 MiB。Windows 上以实际分配空间和文件复用情况验收。对只在 D 盘建一个工程的人，第一次准备可能略多占空间，收益主要来自后续工程、另存和导入。

## 实施顺序

### 1. 先打通同盘安装

- [x] 在 `desktop/runtime.cjs` 的离线分支去掉强制 `--package-import-method=copy`，保留 `--offline --frozen-lockfile --ignore-scripts`。沿用 `desktop/projects.cjs` 对随包基线与已安装工程的判断，已准备好的工程直接打开。
- [x] 在 `test/desktop-runtime.test.ts` 复用已有的命令记录方式核对安装参数。用实际 pnpm 从一个同卷 store 安装两份相同工程，验证依赖可以从各自工程路径解析，并确认大包文件复用。

### 2. 给跨盘工程准备目标卷缓存

- [x] 在真正需要安装时选择 store。将 `dependencyPreparation` 给出的随包 store 作为种子来源，在 `desktop/runtime.cjs` 调用独立的 `desktop/dependency-store.cjs` 做选址和填充。查询 store 使用与安装相同的内置 pnpm、工作目录和环境。比较实际卷和解析后的路径，覆盖目录联接场景。轻量版和直接重开的工程无需扫描种子。
- [x] 在 `desktop/scripts/prepare-offline.cjs` 的干净 store 准备完成时记录本次随包基线的文件清单和基线标识，区分锁文件、目标平台与 store 格式。这样即使用户后来给某个工程装过额外依赖，向其他卷播种时也只遍历随包文件。新桌面资源携带清单；缺少清单的旧资源走已有的随包安装路径。
- [x] 首次使用目标 store 时，只补缺失的包内容和索引，先内容后索引。写入临时文件再完整发布，保留目标 store 已有的文件、包版本和本地构建结果。完整填充后才记录成功。相同基线再次使用时跳过整库遍历；中断后可按现有人工重试流程续补。缓存被清理后，即使旧完成标记还在，也能在 pnpm 报缺包后使标记失效，下一次打开时重新补齐。磁盘满等写入错误要显示原因。
- [x] 将选定的 store 传给实际安装。标准基线沿用离线参数。自定义依赖、较新 Studio 和手动更新沿用原工程的锁文件及普通安装策略，允许获取缺少的包。用已有工程验证切换 store 后的 pnpm 安装行为，保护用户文稿，避免批量重装历史工程。日志记录种子位置、实际 store 位置及首次准备或复用。

### 3. 走通用户实际操作

- [x] 在两个真实 ext4 卷完成开发机验证。以 Windows x64 目标依赖在工程卷不同父目录新建 A 和 B，安装使用离线模式。分别记录首次填充量、A/B 的新增磁盘空间、安装耗时和下载包数。同卷用同一套模板强制复制作为对照。目标为两次下载均为 0，B 不再跨卷搬运整套种子，B 的新增依赖占用低于该机复制对照的 20%。检查代表性大文件的硬链接或写时复制，不能只看资源管理器的目录大小。
- [x] 对已有部分缓存、两次同时初始化、首次填充中断、目标目录不可写分别验证可复用或可恢复。另测旧工程已安装时直接打开，以及自定义依赖工程新增一个包后按自己的锁文件启动。永久测试集中覆盖选址、重复填充与失败恢复，已有工程和导出行为优先复用现有测试。
- [x] 在 Linux 原生工程实测目标卷另存为、工程 ZIP 导出后导入另一目录，以及导出网页播放包。工程 ZIP 应包含源码、素材、锁文件和工程选用的 Studio tgz，排除 `node_modules`、store 与本机缓存路径。导入方用自己的缓存或匹配的完整版恢复，播放包继续独立启动。沿用 [工程 ZIP](../../../node/project.ts) 和 [网页播放包](../../../desktop/web-playback.cjs) 两个入口。
- [x] 运行 `pnpm exec vitest run test/desktop-projects.test.ts test/desktop-runtime.test.ts test/desktop-update.test.ts test/project.test.ts test/web-playback.test.ts`，并运行跨盘实现新增的针对性测试。将实际验证过的缓存位置、回退行为和分享方式更新到 `desktop/README.md`，区分开发机结果与 Windows 实机结果。
- [ ] 在原生 Windows x64 的两个 NTFS 卷完成最终验收。将完整版放在 C 盘，断网后在 D 盘的不同父目录新建两个工程，核对下载数、目标 store、硬链接和第二个工程的实际磁盘增量，再从桌面入口另存、重新导入并验证播放。
