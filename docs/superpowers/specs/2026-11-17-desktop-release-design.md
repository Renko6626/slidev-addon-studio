# Windows 便携客户端发布设计

状态：用户已选择 ZIP 便携版、手动下载升级的路线；以下具体设计待确认。

## 目标与使用场景

使用者能找到一个明确的稳定客户端下载地址，在客户端查看当前版本和本版更新日志，手动检查新版，再到发布页下载 ZIP。完整解压新版后继续打开原工程。发布者能用现有本地打包脚本维护轻量版及可选离线完整版，让更新日志、下载文件和版本号对应。

用户已选择优先简单、易维护的方案。继续使用 Electron Forge ZIP、现有 GitHub 仓库和 npm Studio 包；客户端发行不需要新增后台服务、数据库、安装器或自动替换程序。

## 现状

- 桌面壳版本 0.5.1，Studio 已发布 0.5.2，两者独立。根包与桌面依赖保持现有锁文件。
- scripts/release.cjs 已支持分别改版本、本地构建、归档 ZIP/tgz/SHA256，以及手动上传 GitHub Release。正式构建从 npm 获取指定的精确 Studio 包。
- 当前发布脚本缺少预发布参数，桌面更新日志可缺省并回退到自动提交记录。
- 桌面目前仅检查和更新工程内的 Studio 包，不能检查桌面壳自身的新版本。
- 同仓库已有 npm 版本 Release，无桌面 ZIP Release；直接使用 GitHub releases/latest 不能可靠区分桌面客户端与 npm 版本。
- 本方案只写设计；发布、打包或推送标签继续作为明确执行动作，不把路线确认当作已发布。

## 已选路线及取舍

1. **ZIP 便携版，手动查新和下载（用户已选择）**：沿用已有 Forge 与分发方式，增加版本信息和更新日志，用户解压新版后使用。
2. 安装器与客户端自动更新：能自动安装，但需要接入另一套 Windows 分发和更新链路。本轮沿用第一条路线。

以下具体入口、文件安排和首版版本号是本设计建议，尚未当作用户确认事项。

## 用户可见行为

### 入口与版本信息

- 欢迎页提供一个“版本与更新”入口，对话框内可手动检查客户端更新；保留现有“检查 Studio 更新”，将文案补充为“更新工程内 Studio”，说明它只影响编辑器包。
- 原生菜单增加“帮助”，包含相同的版本信息与客户端查新入口；打开工程时也可通过 Alt 使用，不依赖工程 Vue/Vite 编译。
- 沿用原生对话框，无新网页或编辑器面板。“版本与更新”显示桌面客户端版本、随附 Studio 版本和随包的本版更新日志，离线可查看。
- “检查客户端更新”只在用户点击时联网。结果显示当前版本、最新稳定版及简短说明；“查看更新与下载”在系统浏览器打开该版 GitHub Release，提供完整日志与两种 ZIP 选择。没有更高版本时如实提示。
- 检查失败显示原因，允许手动打开固定的 GitHub Releases 页面。保留当前编辑与工程进程，由用户人工重试。
- 查新和浏览日志不保存、重启或修改工程，不下载或覆盖客户端文件。首页查新不显示为“工程准备”进度。

### 查询来源与选择规则

- Electron 主进程匿名读取固定仓库 Renko6626/slidev-addon-studio 的 GitHub Releases API；不在客户端分发 GitHub 凭据。
- 候选必须是已发布且非预发布的 desktop-vX.Y.Z 标签，并带有匹配该版本的 Windows x64 轻量 ZIP。离线完整版可选。
- 按 X.Y.Z 数值比较选择最新候选；忽略 npm 的 vX.Y.Z Release、草稿、预发布和缺少核心下载文件的记录，不把预发布展示为稳定版。
- 读取发布列表使用 GitHub 标准分页，遇到下一页时继续，直到读完；请求串行，无缓存数据库或后台轮询。每次查询使用整体超时，失败即提示，保留手动打开发布页的入口。
- 原生浏览器跳转只接受固定仓库的 Release 页面；不渲染远端 HTML，不执行发布说明中的链接或代码。对话框将说明作为普通文字展示。

## 更新日志与随包信息

- 每个桌面版本必有 docs/releases/desktop-X.Y.Z.md。它是本版用户日志的唯一源，正式打包/上传时缺失就停止，取消自动生成提交记录的回退。
- 文案围绕“新增、改进与修复、升级说明、已知限制”，空分类可省略。记录随附 Studio 版本、轻量版/离线版差异，以及已有工程是否需要单独升级 Studio。
- prepare.cjs 把桌面版本、随附 Studio 版本和日志原文写入 studio-resources/desktop-release.json；随现有资源目录进入 ZIP。该文件只用于本机展示，不写入演示工程或用户数据目录。
- GitHub Release 使用同一 Markdown 原文；客户端“查看更新与下载”打开同版 Release，不另外维护一套在线日志服务。

## 发布与稳定版流程

- 首个采用本流程的桌面版本建议为 **0.5.2**，随附已发布的 Studio **0.5.2**。以后继续独立维护两个版本；客户端主版本面向下载者，日志记录随附编辑器版本。
- 沿用 desktop-vX.Y.Z 标签和原 ZIP 文件命名，保留 SHA256SUMS-online.txt、可选 SHA256SUMS-offline.txt 与随附 addon tgz。轻量版作为每次桌面发布的必要产物；离线版可选。
- 发布者按精确源码提交打标签，先完成本地构建与校验，再上传为 GitHub 预发布。本地 publish 增加明确的预发布选项，并以预发布作为新建 Release 的默认行为。
- 实机试用通过后，发布者明确把同一 Release 提升为稳定版；提升只修改发布状态，保持标签和产物字节不变。已有稳定 Release 不会因补充离线版被自动改回预发布。
- 稳定版可置为 GitHub Latest，客户端仍按 desktop 标签和资产筛选。npm Release 与客户端稳定版分别管理。
- 本轮保持本地构建、手动上传与手动提升稳定的流程；现有 npm v* 标签发布 workflow 保留，desktop-v* 不触发 npm 发布。
- 已发布文件不覆盖；修改 ZIP 内容时使用新的桌面版本。用户完整解压到新目录后运行，再打开原工程，避免把旧目录残留文件混进新版。

## 代码职责与边界

- desktop 的发布查询小模块负责 GitHub 元数据读取、候选筛选、版本比较和结果整理；复用现有简单版本比较函数。
- desktop/main.cjs 负责原生对话框、固定发布页跳转、菜单及主窗口动作。欢迎页通过已有受限的 studio:project 动作入口发起“版本信息/客户端查新”，保持现有主窗口校验。
- welcome.html / welcome.js 做少量入口和请求状态调整，沿用现有样式。使用独立的查新按钮等待态，保留工程准备状态的原含义；不增加恢复状态机。
- desktop/scripts/prepare.cjs 及 scripts/release.cjs 负责生成随包日志、检查版本/产物与预发布上传。Studio addon、公共 runtime、线上工作台和已有工程依赖格式保持原边界。
- Studio 包更新仍使用现有 npm 查询、归档校验、保存和重启流程；客户端查新不调用它，也不因换客户端而改写已有工程的 Studio 依赖。

## 验证与交付边界

- 新增测试只覆盖本次关键行为：桌面 Release 筛选（含 npm/预发布/草稿/资产不符）、数值版本比较、查询失败，以及随包日志与必填发布日志检查。复用现有 release/desktop 测试，不新增浏览器交互测试工程。
- 集中运行受影响的既有测试、必要类型检查与发布命令 dry-run。设计文档改动不运行产品测试；完成实现后再做一次相关检查。
- 若进入实际打包，检查 ZIP 中 exe、随附 Studio、日志、模板和 miniserve，并保留校验表；轻量版必需，离线版按本次明确交付要求制作。
- Windows 人工试用聚焦：解压启动；新建及打开旧工程；编辑后保存重开；工程字体与网页播放包的基本可用性。Linux 打包/文件验证不能替代这些结果。
- 取得真实 Windows 反馈前使用预发布状态，不声称已完成稳定版验收。线上工作台不随本轮桌面工作重新部署。

## 交由实现者决定

查询模块和本地资源读取辅助函数的文件名、原生对话框说明截取长度、少量错误文案及测试夹具组织，可按现有代码习惯处理。界面沿用当前样式，不重新设计欢迎页布局。若发现需要更换打包框架、增加服务或扩展宿主公共接口，先作为新决策提交。
