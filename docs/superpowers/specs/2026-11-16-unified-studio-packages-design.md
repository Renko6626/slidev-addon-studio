# Studio 包获取、安装与更新统一设计

## 目标和已确认模型

用户已确认：轻量版与完整版只区别随附依赖的范围；两者都携带 Electron、桌面程序、pnpm、模板和 Studio tgz。完整版额外携带标准工程的依赖缓存。随附 Studio 与联网获取的 Studio 使用相同归档格式、工程安装方式和手动更新入口。

日常修改编辑器只发布 Studio npm 新版本。桌面壳承担窗口、文件操作、包更新和进程启停，按需独立发布。工程保持普通 Slidev 目录，保留人和 agent 修改的文稿、组件、素材和既有依赖。

本轮授权为制定计划，不写产品代码、不安装新依赖、不构建桌面包、不提交、不发布。下文“推荐细节”是把已确认模型落成可执行计划的建议，供实施前核对。

## 方案和取舍

| 方案 | 取舍 | 结论 |
| --- | --- | --- |
| 随附和在线都取得明确版本的 tgz，再统一安装 | 延续现有本地包与可携带工程；需要一个很小的 Studio 归档目录 | 用户选择的路线 |
| 在线用 npm 别名、离线用 file 引用 | 包管理器负责下载，但工程中出现两种依赖来源和切换规则 | 不采用 |
| 自建本地注册库或包管理系统 | 需要额外服务和元数据维护，现有规模用不到 | 不采用 |

tgz 是可分发的归档；pnpm store 是包管理器维护的安装缓存；node_modules 是工程实际使用的依赖。仅统一获取与安装流程，不自行实现 pnpm store、复制其内部索引或把所有第三方依赖逐一转存为 tgz。

## 推荐细节：版本与归档

- Studio 正式发布继续使用 `X.Y.Z`，按三个数字比较，不能按字符串比较。仅跟踪 npm `latest`，不增加测试通道、版本历史 UI 或任意包安装入口。
- 同一个 Studio 版本的随附与云端 tgz 应来自同一发布产物；有源码变化必须递增版本。推荐正式 `release:build` 获取根 package.json 所指定、已经发布到 npm 的精确版本 tgz；先发布 Studio，再打需要随附它的正式桌面包。未发布就明确停下，不能静默改用工作区源码。`desktop:dev` 保留从当前源码 pack 的开发流程，不新增正式更新通道。现有正式版号约束不改成一套通用 SemVer 引擎。历史非正式版工程可以继续打开，更新入口明确提示版本不适用，沿用显式启用已知正式包的能力，不自动重写。
- 随附归档保留 `studio-resources/slidev-addon-studio.tgz`。构建时额外写 `studio-resources/studio-package.json`，只包含 `{ name, version, integrity }`；name 是 `@renko_1055/slidev-addon-studio`，integrity 是 tgz 的 SHA-512。不要再从桌面 package.json 推断 Studio 版本。
- 下载的归档放在 `app.getPath('userData')/studio-packages/slidev-addon-studio-X.Y.Z.tgz`。不覆写应用目录、不创建数据库、当前版本指针或下载任务记录。可用版本来自随附描述和已完整写入的版本归档。
- 工程中新安装/更新的包放在 `vendor/slidev-addon-studio-X.Y.Z.tgz`，依赖仍叫 `slidev-addon-studio`，值为对应 `file:vendor/...`。版本写入文件名使 pnpm 能识别一次明确的包变更，避免重复替换固定路径而沿用旧解析。
- 旧工程的 `file:vendor/slidev-addon-studio.tgz` 继续可用；只在主动升级时切换成版本化文件名，不做批量迁移或历史包清理。
- 读取当前运行版本以工程 `node_modules/slidev-addon-studio/package.json` 为准；新格式依赖路径提供预期版本，锁文件一致性和关键入口用于判断是否需要安装。未知/缺失版本不伪装成最新版。

## 包获取与选择

新增一个只在桌面主进程使用的小型 CJS 模块 `desktop/studio-packages.cjs`，负责：读取随附描述、列出本机已取得的 Studio 归档、比较版本、查询官方 npm、下载归档。它不修改工程、不管理 Slidev 进程。

- 普通启动和新建工程不查询网络。从随附包与已下载归档中选最高正式版本。
- “检查 Studio 更新”查询 `https://registry.npmjs.org` 中固定包 `@renko_1055/slidev-addon-studio` 的 latest 元数据；取得版本、tarball URL 和 integrity。轻量版、完整版入口相同。
- 检查只读取元数据；用户选择更新/下载后才取得归档。比较时同时考虑本机可用版本，不能因云端 latest 较旧而降级。
- 下载完成后核对名称、正式版本和 npm 提供的 SHA-512，再写入正式缓存文件；失败不产生可选归档，也不修改工程。一次请求失败就显示原因，用户可重新点击；不增加自动重试、队列、断点续传或恢复状态机。
- 第三方依赖仍交给随软件的 pnpm；tgz 已在本机不代表它新增的依赖也已准备好。

## 工程与 pnpm 安装

`desktop/projects.cjs` 负责工程中的依赖声明和 tgz 复制；所有来源统一接收 `{ name, version, archive, integrity }` 包描述。主流程先选包，再调用工程操作。

- 新建：使用本机最高可用 Studio，复制模板与该版本归档，生成普通 manifest。
- 打开：保留工程自己的版本；缓存或云端出现新版不会触发升级，不再提示用较旧随附包覆盖已经管理的工程。
- 另存：继续带走工程使用的 tgz，之后按该工程版本准备依赖。
- 主动更新：只改 Studio 依赖与对应归档，允许 pnpm 调整其必要传递依赖；不批量升级 Slidev、Vue、主题、Pinia 或 agent 添加的其他直接依赖。安装错误按既有流程显示，不额外开发依赖兼容性分析器，也不自动更改其他直接版本约束。

完整版中，只有所选 Studio、标准 manifest 和锁文件仍匹配随附基线时，才复制基线锁文件并使用既有 `--offline --frozen-lockfile` 安装。若新建时选中了较新的缓存包，或用户更新到新包，则沿用普通安装、允许下载缺少的依赖；不得把旧离线锁文件套给新 Studio。离线基线失败仍按现有规则报错，不静默转联网。

`desktop/runtime.cjs` 继续只负责 pnpm 和 Slidev 子进程。保留普通缓存行为和完整版现有 store 位置；安装计划明确携带 `{ needsInstall, storeDir?, offline }`，让普通安装也能复用现有完整版 store。不得为统一形式增加全量缓存搬家或每次启动复制数百 MiB。

## 更新入口和生命周期

首页提供“检查 Studio 更新”，工程“文件”页提供同一能力。推荐复用原生对话框呈现版本和确认按钮，不另建版本管理页面。

- 无工程：显示“本机可用 / 最新发布”，可“下载更新”；只更新本机归档，新建工程随后采用它。
- 有工程：显示“当前工程 / 本机可用 / 最新发布”，可“更新并重启编辑器”；仅影响当前工程。
- 没有新版本或本地版本较新：给出实际版本信息，不降级、不安装。
- 正在准备工程或更新时，复用既有 `working`、进度事件和日志，防止同时切工程；日志入口继续可用。
- 下载归档时可让当前编辑器继续运行。确认应用更新后，先调用已有保存接口；保存失败不停止编辑器、不改工程。保存成功后停止旧进程，复制/声明新包、安装并重新打开。
- 安装或重启失败：停下，返回准备页并显示日志位置；工程文件保留实际状态，可人工重开/重试。不承诺事务式回滚、不新增备份或自动恢复系统。
- 手动检查网络失败不关闭当前工程。正常打开、继续编辑不以云端可访问为条件。

`desktop/preload.cjs` 仅增加固定的 `studioUpdate()` 能力，主进程自行决定包、版本和路径。渲染端不能传任意 URL、包名、文件路径或 shell 参数。主窗口 IPC 的 sender 检查沿用现有规则。

`client/project-host.ts` 将新能力声明为可选；`StudioFile.vue` 仅在宿主提供该方法时显示入口。新 Studio 在旧壳或独立浏览器里仍可编辑；旧 Studio 没有文件页入口时，新壳首页仍能检查和下载更新。

## 桌面版本与发布

根 package.json 的 Studio 版本与 desktop/package.json 的壳版本分别维护。建议版本命令明确指定 `studio` / `desktop`；打桌面包时记录所附 Studio 版本，取消两者必须相等的检查。

推荐保留 `vX.Y.Z` 作为 Studio npm 发布标签，桌面 GitHub Release 使用 `desktop-vX.Y.Z`，避免同一标签同时代表两个独立产品版本。桌面 ZIP 名称和归档目录用壳版本，Studio tgz 名称用 Studio 版本，校验表记录实际文件。每次正式分发内容不同的桌面 ZIP 都使用新壳版本；日常 Studio 更新不重打 ZIP。

保留 `--offline` 构建选项与既有 online/offline 文件名，文档用“轻量版 / 完整版”说明范围；不新增第三种运行模式。npm 发布与本地桌面打包仍是不同动作，不在本轮自动推标签、上传 GitHub 或发布 npm。现有 npm 工作流只需将版号校验改为直接读取根 package.json，避免间接调用带桌面版本约束的 releaseInfo；不新增云端构建或检查工作流。

## 验证范围

复用 Vitest、临时文件和真实生产函数。重点覆盖数值版本比较、可用包选择、网络检查不改工程、实际下载字节校验、版本化依赖写入、直接依赖保留、旧工程保持原版本、更新后重开不降级、离线基线只用于匹配工程，以及版本解耦后的归档。

下载测试使用本地 HTTP 服务、临时目录和实际响应字节，不访问真实 npm；编排测试只替代 Electron 对话框/进程边界，断言实际工程 manifest、归档字节和结果，不用源码字符串或 mock 调用次数替代行为。

实施完成集中运行相关已有/新增测试、TypeScript、Vue SFC 检查、受影响 CJS 语法检查和 release dry-run。默认不运行真实 npm 更新、重复全量联网安装、正式桌面打包或 Windows 自动化。浏览器验证至多导航、初始化截图状态和查看截图，不点击、输入或执行交互流程。真实 Windows 对话框、系统路径和网络更新由后续试包验收。

## 范围限制

不做 Electron 自动更新、后台定时检查、批量升级所有工程、任意版本选择 UI、回退按钮、自建注册库、多下载并发、故障恢复机制、通用插件升级框架或自动清缓存。发现超出上述路线的架构选择，实施者先报告，不自行扩展。

## 设计检查记录

一次只读 builder check 提出正式桌面包如何与 npm 共用同一产物的问题；上文已明确推荐“正式构建下载已发布的精确版本，开发启动保留源码 pack”。其余未发现需要用户补充才能计划的重要缺口。该发布顺序、版本化工程文件名和桌面独立标签均作为本计划推荐细节展示，不冒称已逐项确认。
